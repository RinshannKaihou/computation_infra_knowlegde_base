## 修订后的重点边界（2026-10-09）

- **CUDA Graphs 约束两档与 non-captured 限定（B16-C01，P1）**：Constraints 按原文两档分列——非默认流捕获、禁止 CPU↔GPU 同步（`.item()` 等）、多 generator 须 `register_generator_state` 注册并用 graphsafe API，违反**多半**（likely）runtime error；同进程同时只能一个 capture、捕获期间进程内（任意线程）不得有**非捕获 CUDA 工作**（non-captured CUDA work）、CPU 工作不被捕获（replay 时省略）、每次 replay 读写相同虚拟地址、禁止动态控制流／动态形状、多流捕获允许但另有限制，违反**多半**静默数值错误或未定义行为。两档均为 likely 措辞——既非必然报错也非必然无报错；第二档违反「可能不报错，不能依赖异常检测排除，须靠核对清单」，不得写成「不会被报错暴露」的绝对断言。
- **901「先前错误致失效」定义与 NVIDIA 简表场景分离（B16-C02）**：CUDA Runtime API 12.8 `cudaErrorStreamCaptureInvalidated` 与 HIP `hipErrorStreamCaptureInvalidated` 的通用释义为「先前错误已使当前捕获序列失效」，定性须追溯**首个**捕获失败（同线程先前非法调用、900→901 级联均落在定义内）；NVIDIA capture-failures 简表「external work or thread」是页内场景化概括、粒度粗于 Runtime API 定义，只作具体场景引用、不作 CUDA/HIP 共用归因。
- **Mega-Cache API 非 2.6 与 TritonBundler 实现映射三层区分（B16-C03/C06）**：`save_cache_artifacts()/load_cache_artifacts()` 不在 v2.6.0 固定源码（`torch/compiler/__init__.py` 无定义），按「较新教程能力（非 2.6）」单独标注，最低可用版本未取得（教程「PyTorch 2.4 or later」总前提不证明逐接口在 2.6 可用）；教程 `InductorCache` 是「FXGraphCache 与 Triton cache 的组合」**概念名**而非同名类存在性声明，2.6 已有实现映射（`TritonBundler` 记录/收集/恢复生命周期、compile_fx cache-miss 保存路径、codecache 命中恢复路径、开关 OSS 未覆盖默认 True 且实际路径受 `force_disable_caches` 控制）——第一轮修订曾以「无同名类」判其非 2.6，属误判已撤销并如实记录；Triton 相关缓存三层区分：`TritonCodeCache`（经 PyCodeCache.load 加载生成的 Python kernel 模块，非 cubin 产物缓存）／Triton 编译器自身产物缓存（compiler.py 独立命中路径）／PyTorch 侧打包（TritonBundler）。
- **test_cache_guard 降级为复合变化观察（B16-C04）**：`val=6→4` 同时把执行分支 sin 改为 cos、FX 图本身变化——该测试只证明「图变化（伴随 guard 值变化）时 cache miss 且不误复用」；guard 值独立进入缓存 key 的隔离证据未取得；`FxGraphCache._lookup_graph` 先按 key 取候选、再对候选求值 guard 表达式，不能简化为「guard 值不同即不同 key」；编译配置进入 key 由 `test_hash_config_changes` 单独支撑。
- **冷缓存两维度：新进程启动≠冷缓存启动（B16-C05）**：`TORCHINDUCTOR_FORCE_DISABLE_CACHES=1` 只禁 **Inductor 层**缓存（config.py L90–91 注释原文限定），不是全栈冷启动、也不等于「缓存机制正常开启但目录为空」的冷启动条件；冷缓存测量须同时处理两个独立维度——进程内状态（新进程或进程内重置，说明方式）**并**使测量范围内相关持久化缓存（Inductor/Triton/远程）处于**已说明的冷状态**（记录实际生效目录、远程缓存处理方式与清理范围，保留命中/未命中观测）。显式 `TRITON_CACHE_DIR` 不随 `TORCHINDUCTOR_CACHE_DIR` 更换而变；FXGraphCache 按 key 从磁盘/远程读取候选、Triton 编译器读自身缓存元数据直接返回产物——只重启进程而保留磁盘缓存称「新进程启动」，不能称「冷缓存启动」。
- **Triton CI pin 取证链（B16-C07）**：PyTorch v2.6.0（commit 1eba9b3）`.ci/docker/ci_commit_pins/triton.txt` 第 1 行内容即 `35c6c7c6284582b3f41c71c150e11b517acf074a`——该 commit 与 v2.6.0 的关联是 **CI commit pin 的直接记录**，非仅凭版本字符串推断（第一轮「钉的是版本号非完整 commit」表述有误已更正；`.ci/docker/triton_version.txt` 钉 3.2.0 与之并存）；范围限定：证明 CI 源码 pin 关联，不自动证明所有 PyTorch/ROCm wheel 或本地安装使用同一 Triton commit。
- 其他批次边界：ROCm 10.1.0 兼容矩阵与安装页为 JS 选择器单页、无深链（引用须注明选择器状态与观察日期）；HIP 文档站标 7.16.0 vs 组件表 HIP 10.1.0、llvm-project 站标 22.0.0 vs 组件表 24.0.0 两处站标冲突，组件版本以 release notes 组件表为准并注明差异；docs-10.1.0 无 pytorch-compatibility 页（7.2.3/7.1.1 为不同版本线，ROCm 10.x 文档体系内无 torch.compile 专项说明页，ROCm torch.compile 逐项限制保留 unknown）；上游 wheel 索引 ROCm 目录只到 rocm7.14、ROCm 10.x wheel 由 AMD 索引分发（不能写成「PyTorch 官方 wheel 已覆盖」）；cuDNN/NCCL 不在 CUDA Toolkit 12.8 组件表为结构性负面证据（组件表不收录 + 独立文档树 + 容器清单分列），无一句官方直述；CANN 编译器组件职责页缺口与 CANN 8.3.RC1 精确 HDK/OS 交集 blocked 保留；TorchAir 全线试验特性（beta、aclgraph 产品矩阵限 Atlas A2/A3、缓存跳过 Guards 且要求脚本一致、CANN 跨版本缓存不兼容）；主案例 #188641 的回归测试带 `@skipIfRocm`——CUDA 侧已修并有回归、ROCm（hipsolver 路径）保持 unknown；#193735 为「无法复现后关闭」，不作已解决缺陷引用；`@skipIfRocm` 标记不当作 HIP 测试通过。全部正文未执行真实环境验证。
