# Batch 17/18 独立审阅流程与归因意见

独立意见日期：2026-10-10。审阅角色未参与历史评审或本批写作；按本次明确指定的 `gpt-6.1-sol / xhigh` 配置工作。本文只审计验收标准、发现与复核计数、关闭条件、历史对照和模型归因边界，不代替另外两位独立评审的技术全文核验。不修改原作者记录、历史评审结论、来源登记、任务状态或知识正文；唯一输出是本附件。

## 结论

1. **两批确有应该打回的初稿问题；“频繁打回完全是评审苛刻”不成立。** 图和验证设计缺失、未冻结工具/框架版本、来源存在性被扩成技术保证、统计和完成语义错误，均能对应原验收。尤其 Batch 18 的 procedure 在型号/指标/输入仍待选择时已交付，不能因诚实标为 unknown 就算方法完整。
2. **“6 次和 4 次复核证明初稿低劣六次/四次”也不成立。** Batch 17 第三次已经关闭 12/13，后续只有 C08 的证据尾部和补证新增表述；第四、六次明确无新增修改项。Batch 18 的 15 项初审包含一项审阅者错误，净有效初稿发现为 14；C16 是修订引入，不能追记给初稿。复核次数、问题数、唯一根因数和模型样本数不是同一统计。
3. **两批有效初审问题数均比 Batch 15/16 更多；首轮关闭比例须分别比较：B17 的 61.5% 低于 B15 的 85.7%，与 B16 的 60.0% 相近；B18 的 42.9% 同时低于这两个基线。不能据此支持“较所有历史批次显著退化”。** Batch 13/14 的初审规模与本次接近，且有 P1；Batch 13 还经过额外独立补审。各批同题、材料、任务数量和评审粒度并不相同。
4. **原评审的主要技术门槛合理，但确有值得纠正的流程问题。** B18-C01 错读上游表格；统计仍把撤销项混进 CLOSED。B17-C08 的初稿补有限样板要求合理，但尾部将“具体算子的累加 dtype + TorchNPU 到 cubeMathType 的固定实现关联”一并称为原强制门槛，超出原清单的明确程度，存在验收解释加强。研究记录单点错误应作为 P3 编辑同步处理，不能将技术主体已接受再表述成同一技术问题未修好。
5. **接受用户关于切换 Muse Sparks 1.3 的事实陈述；本资料不能隔离模型的净效应。** 可以据此管理这条写作流水线，不能把这些异题批次当成模型泛化能力测评。

## C08 的标准张力：不能只为原评审辩护

原 T02-10 objective 确实写“计算/累加精度”（规划 `:4647`），acceptance也要求区分这些概念（`:4649`）；因此不能读成“Ascend任何资料都可以不补”。原 source_discovery 指定 CANN/TorchNPU 的 dtype/format转换及计算精度（`:4663`），初稿却在 Ascend 段 `initial-dtype.md:84–86` 只给 AOL入口，并说转换/计算文件定位待补。**要求补一个有版本和真实支持条件的有限样板是公平的，不构成新任务。**

但同一 acceptance 紧接着写“**格式与精度开关只在对应来源支持范围说明**”；原清单没有写每平台必须取得至少一个算子的累加 dtype，亦未明确要求把 CANN SDK 的 cubeMathType 契约连到 TorchNPU 调用实现才能接受该 SDK 样板。第六次关闭条件 `:34` 则同时要求逐算子累加证据和固定相关计算实现参数/调用关系。这是可以辩论的解释强化，不能仅通过反复称“原强制边界”消除它。
