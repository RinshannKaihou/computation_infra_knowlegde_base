## 发现清单

### C01 · P2 · 将容量评估命令与审计保护工具混成同一对象

- **位置**：正文 L12、L42、L50、L67；取证记录 L9；registry L6958。
- **问题**：正文将触发事件的命令称为“审计命令”，又以“审计命令缺陷”作为已确认共同原因。L42 另写成由自动化工具下发。原文区分容量评估命令与负责审查、阻止危险命令的保护工具；已披露的 bug 在后者。现有写法混淆触发操作和保护失效，也容易把未能阻止执行误读成执行中无法停止。两份本地来源记录重复了这一混写。
- **证据**：[Meta 复盘](https://engineering.fb.com/2021/10/05/networking/outage-details/)的维护段分别描述命令意图及审计保护失效，没有披露具体下发实现。原文不支持将两者合并为一条有缺陷的审计命令，也不足以确定自动化下发路径。
- **关闭条件**：正文、取证主张表和 Meta notes 统一分开记录“容量评估命令产生全局影响”与“审计工具缺陷使保护未能阻止”；命令内容、执行机制及缺陷机理保持 unknown。共同原因分析保留运营方披露的全局作用范围，不能只替换名词而继续合并两类对象。

### C02 · P2 · 在无内部时刻的复盘中补入分钟级间隔，并混用发现时刻与事件时刻

- **位置**：正文 L54–55、L58、L61、L68、L86；取证记录 L10/L32；registry L6969。
- **问题**：L55 将 Meta 的 DNS 撤告标成“随后数分钟”，但原文只有快速发生的定性描述；该行紧随 15:58 外部发现撤告之后，表格顺序还会使同一撤告看起来又发生一次。L68 将 15:58 写成前缀消失时刻，而原文是 Cloudflare 注意到已经停止宣告的时刻。恢复行的“判定重新接入”也省略了原作者的暂定语气。
- **证据**：[Meta 复盘](https://engineering.fb.com/2021/10/05/networking/outage-details/)没有这段分钟耗时；[Cloudflare 博客](https://blog.cloudflare.com/october-2021-facebook-outage/)分别提供外部发现时刻与解析可用性更新，并保留 21:28 重连判断的不确定性及应用恢复仍需时间的边界。Meta 的因果叙述可以支持骨干先于 DNS 撤告的机制顺序，不提供与这些外部时刻的精确对齐。
- **关闭条件**：删除无据的“数分钟”；将内部机制顺序与外部时间轴分开或明确标为“Meta 未给时刻，非承接上一外部时刻”。15:58 全文统一为发现/注意到的时刻，保留 ~15:40、~15:50、15:51 的不同语义；21:28 表述为外部看来重连、非全服务恢复验收。同步相关取证表和 notes，不能通过给 Meta 补写时刻来消除差异。

### C03 · P2 · 将作者的全球性描述升格为全互联网直接测量

- **位置**：正文 L56、L69，尤其 L69“Cloudflare 观测”“对象是全互联网解析器”及“缺失证据＝无”；取证记录 L10；registry L6969。
- **问题**：30 倍这一数值并非错引，原文确实有全球解析器的概括；问题是正文把该概括无条件列成覆盖全互联网的直接观测。原文展示的数据视角是 1.1.1.1，未提供全体解析器的采集范围、分母、聚合方法或一致增长证据。将缺失证据填成“无”，掩盖了这个覆盖缺口。
- **证据**：[Cloudflare 博客](https://blog.cloudflare.com/october-2021-facebook-outage/)的 DNS 影响节先说明图中流量来自其 1.1.1.1，再给出全球性的 30 倍描述；二者证据层级不能合并。SERVFAIL 缓存及多个公共解析器失败另有叙述/示例，不等于都测得同一增长倍数。
- **关闭条件**：区分 Cloudflare 自身观测与作者对全球影响的描述；如保留 30 倍，明确归属于作者表述并记录全球测量口径未披露。不得反向宣称所有解析器或所有 DNS 查询均已直接测得 30 倍；L69 缺失列、取证记录与 Cloudflare notes 同步收缩。对 Meta 恢复影响未知的现有边界继续保留。

### C04 · P2 · 将未披露的正常域名对照写成反驳证据

- **位置**：正文 L71；取证记录 L27 的“两个被反驳假设”；registry L6969 末句。
- **问题**：L71 用“其他域名解析正常”反驳 Cloudflare 自家解析器故障，但两篇原文没有给出这项按域名对照的检查记录。原文报告的多数请求低延迟和整体影响较小，不能自动改写成特定正常域名对照。结论方向可以有依据，反驳证据本身仍须真实且限定对象。
- **证据**：[Cloudflare 博客](https://blog.cloudflare.com/october-2021-facebook-outage/)提供其他公共解析器的同类失败示例、BGP 撤告观察及其自身服务表现；这些足以削弱“1.1.1.1 独有问题解释本次 facebook.com 失败”的假设，不证明已经排除 Cloudflare 的所有潜在独立故障。
- **关闭条件**：删除无出处的正常域名对照，改用原文实际展示的多解析器失败/BGP 证据，并把被反驳命题限定为该事件的解释。若保留正常域名对照，须补精确原始记录并明确是新增证据；不得用排障常识填入原作者调查。取证表对“反驳”的概括应与修订后的命题一致。

### C05 · P2 · 把健康性和可达性两个属性称为两个故障域

- **位置**：正文 L68、L79、L91；对照 `dimensions-and-failure-domains.md` L83–100。
- **问题**：L79 将“服务健康性与网络可达性”直接定义成两个故障域；它们是不同检查属性/服务条件，不是两组已界定的受影响对象。L68 进一步使用“进程健康”“不是 DNS 自身故障”，容易混淆服务器仍运行与 DNS 对外服务已经失效。源文没有提供进程健康检查记录。
- **证据**：[维度与故障域](../../knowledge/08-reliability/dimensions-and-failure-domains.md)按共享依赖和影响范围定义域；[Meta 复盘](https://engineering.fb.com/2021/10/05/networking/outage-details/)只支持 DNS 服务器仍运行而不可达，以及连接条件驱动撤告。其健康判定指向网络连接条件，不是进程健康测量。
- **关闭条件**：改为区分“仍在运行”“对数据中心的连接条件”“对外可达/解析服务”三个边界；说明这是骨干失效向 DNS 服务的传播，不是已有证据确认 DNS 进程独立损坏。删除两个属性等于两个域的定义；若讨论不同故障域，须给出对象、共享依赖和作用范围，并与关联正文一致。

### C06 · P2 · 将未披露的物理冗余布局及 anycast 实现写成案例架构事实

- **位置**：正文 L76–78、L99；取证记录 L27/L31。
- **问题**：L78 从一次命令影响全部连接，扩写成“物理上冗余”的连接及同一批次/控制路径实现；L99 另列 DNS anycast 式宣告为该环境事实。来源足以证明全局变更影响边界，但未披露物理备份布局、独立路径关系、批次实现或这里的 anycast 机制。分析冗余独立性可以迁移，不能因此补齐原案架构。
- **证据**：两篇指定原文均未说明上述 anycast 实现；[Meta 复盘](https://engineering.fb.com/2021/10/05/networking/outage-details/)未给连接冗余布局和命令下发细节。取证记录本身已将拓扑与 DNS 部署细节列为 unknown，与正文的确定措辞不一致。
- **关闭条件**：事实层只保留运营方披露的全连接共同受影响及 BGP 宣告/撤告；删除无据的物理冗余、anycast 和批次实现断言，或另补精确原始证据。将控制面/变更域、冗余独立性分析及 GPU/NPU 对象映射显式标为本库归纳，不能据分析反推拓扑。正文与取证 unknown 清单同步，平台边界宜表述为本案例材料不涉及 GPU/NPU，而非证明 Meta 实际系统不存在这些组件。

### C07 · P2 · 将主用与带外同时失效提升为已确认共享依赖

- **位置**：正文 L43、L57、L80、L109；取证记录 L9/L31；registry L6958。
- **问题**：L80 以“运维通道与被管系统共享依赖”解释带外失效，把内部工具的 DNS 依赖、主用与带外同时不可用连成已确认的共同故障域；但 L109 又正确承认带外具体依赖链 unknown。共同失效是观测，共享机制是待解释的原因，不能只靠并发不可用确认。原文的内部工具影响还限定为许多工具，不是完整依赖清单。
- **证据**：[Meta 复盘](https://engineering.fb.com/2021/10/05/networking/outage-details/)分别披露 DNS 对内部工具的影响与两种访问不可用，没有明确带外依赖 DNS、同一链路、认证或某一其他共同组件。[故障模型](../../knowledge/08-reliability/fault-models-and-propagation.md) L149 也要求区分共享域线索与实际因果证据。
- **关闭条件**：将“许多内部工具受 DNS 影响”与“主用/带外访问均失效、具体机制未披露”分列；共享依赖只作为候选和迁移检查问题，不作为该事故带外失效的已确认原因。正文、取证 unknown 清单和 Meta notes 统一保留此边界；不得只加 unknown 注脚而继续在分析段断言原因。
