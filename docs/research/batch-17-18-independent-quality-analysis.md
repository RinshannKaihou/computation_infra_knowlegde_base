# Batch 17/18 初稿质量与多轮退回的独立归因分析

日期：2026-10-10（Asia/Shanghai）。用户说明这两批写作切换了 Muse Sparks 1.3，并要求指派独立评审分析初稿质量。三位新派子代理分别评审 Batch 17、Batch 18 和原评审流程；原 Codex 主助手组织、核对证据身份并汇总。本报告保留独立评审对原评审的批评，不以原报告的 OPEN 数量直接作质量判决。

**结论：两批初审稿确实低于项目约定的技术交付门槛，技术主张核对不足和必交遗漏足以解释前期返工。多轮打回还包含修订不彻底、修订新增错误、持续缺证和评审问题；不能全部算给初稿，也不能据此认定 Muse Sparks 1.3 导致质量下降。** 对这两批产物质量的判断有直接证据；对模型净效应的判断缺少受控对照。

“发现组”是跟踪 ID，不是全部错误的独立根因，也不是全文事实主张的分母。两位技术评审的主分类略有差异：Batch 18 将关键条件遗漏合入语义类，Batch 17 将部分契约遗漏放入条件/方法类。不可将这些类别比例拼成模型错误率。一个组也可能有多个子问题。

Batch 18 的历史累计 16 个 ID 应拆为 **14 个初稿核心成立 + 1 个评审误读撤销（C01）+ 1 个首次修订新错（C16）**。其五轮 OPEN 出现次数 15+9+5+3+3=35 不是 35 个初稿缺陷。第一次历史“7 CLOSED”包含撤销 C01，不能把它当作者成功修复；有效初稿修复数是 6。

Batch 17 没有新 ID，但 C01/C03/C08/C10/C11 内部有修订新增错误。不能因没有新编号就说修订没有回归，也不能把它们追记为最早初稿已有的错误。六次和四次复核是同八篇内容的重复观察，不是十个独立写作样本。

## 原评审对返工的影响

三位评审没有将打回整体判为不合理，也没有替原评审的每个子指控背书。需明确保留以下校准：

1. **B18-C01 是评审错误。** 相同 SHA 的 HTML 六行 Supported 都为 √，斜杠在 Product 单元格。原主要反证必须扣除，不能算作者模型错误或作者修复成功；其错误转录/分歧处理增加了返工。原记录已经纠正，独立报告仍把它记在评审质量账中。
2. **B17-C07 与 B18-C12 的部分指控过强。** C07 初稿可以理解为“已经返回错误结果才须判错”，不能证明作者把所有病态/非有限输入都判成平台错误；需要可检查反例/残差的核心要求仍成立。C12 初稿已注明扫描/validation 互斥和分开记录，欠的是执行表与覆盖设计，不宜称其完全不知道互斥。
3. **B17-C08 尾部的硬门槛存在验收解释升级。** [T02-10](../../plans/full-coverage-backlog.yaml) L4647–4663 要解释计算/累加概念、补 CANN/TorchNPU 有限语义，但也限定“只在对应来源支持范围说明”。初稿 Ascend 实质缺失，要求补有限样板合理；到第六次，计算逻辑和条件已核实，继续把“某算子官方累加 dtype + 固定 TorchNPU cubeMathType 调用关联”同时作为不可替代硬门槛，不能由原清单唯一推出。沿用初审者的解释不等于原清单已明确规定该深度。应分别记已接受样板、待补覆盖证据和验收解释，不能把纯缺证再算新增写作错误。两位相关独立评审一致提出这一点，详见 [B17 争议](batch-17-independent-quality-audit.md)与[流程意见](batch-17-18-independent-process-audit.md)。
4. **剩余影响应决定严重度与复核量。** B18-C04 后来只剩现行 metadata 同步仍记 P2偏保守；C12 第四轮只剩研究记录 `>0`/`==0` 倒置，应单列 P3编辑同步，技术主体已接受。它不能单独支撑“正文重大技术问题仍未修好”。同期 C10/C14 仍为 P2，纠正这个展示口径不会使 Batch 18 自动通过。

C10 与 C08 不可简单类比：[T03-03](../../plans/full-coverage-backlog.yaml) L4802 明确要求重试、CQE、ECN/PFC 的版本化单位/方向/累计范围。字段继续缺失，相关测量语义确未交齐；诚实禁用判据避免误判，不能代替这一原必交物。独立评审认为 C10 持续 OPEN 有直接依据。

本次是质量/流程归因审计，未以综合意见改写历史关闭状态或宣布新验收通过。C08 的范围争议应另行判定；原稿缺口、已改好的文字和待补证覆盖不应继续混记。

这些不是公平模型试验：题材、取证难度、文档分量、写作/集成流程和发现分组不同；B14把多行错误码合成一个 ID，B17把不同同步/计数问题分开；早批还存在有限审阅通过、覆盖证据缺口并存的先例。各批通过与未知消失也不是同一终态。不能把原始发现密度、轮次或表中比例当模型能力分。

接受用户关于 Muse Sparks 1.3 切换的陈述。当前可证实的是**切换后的这两批送审产物有明显质量问题**。没有同题、同提示词、同冻结证据包、同预算/工具和同集成方式的对照；也不能把每一步取证、集成和修订的新错都锁定到一个具体调用。因此“初稿需要更严的技术核验”有强证据，“Muse 的净能力更弱/就是打回的原因”不能据现有资料确定。没有证据可推断作者赶工、减少预算或故意编造。

## 对后续写作的具体建议

1. **送审前补齐验收卡和主张核对。** 每项明确最小样板、必交图/表/判据、已有精确来源、允许 unknown 的位置。对计数公式、支持矩阵、API 完成语义和源码条件，逐项核对字段、分支及被调用函数；仅有主题来源或 HTTP 200 不足以证明主张。
2. **修订按子项一次同步。** 每个发现记录“原错/已接受/本轮新错/缺证/编辑同步”及对应位置；正文、摘要、登记、当前研究追加节用同一清单核对。检查 `==0`/`>0`、ceil、signaled 和全量/完整清单等容易改变语义的词。
3. **评审把缺证长尾与需改文分开。** 对无新输入、无新增修改项的轮次保留已接受范围和待补证触发条件，不反复将其描述为新写作失败。剩余纯编辑项用短复核，按实际影响重评优先级；评审撤销项另列，不算作者缺陷。
4. **用同题盲评决定模型选择。** 选账户/同步、条件表/指标、EP 消息映射等不同类型的有限任务，冻结相同来源和验收卡，以相同提示词、预算、工具和集成流程多次生成，匿名核对初稿事实冲突、必交遗漏、修订新错及首次闭环。记录每一步实际调用配置。现有两批可以提示这条流水线的风险，不能代替该对照。

建议先修取证到主张、修订一致性和评审终态三个环节，再依据同题对照决定模型选择。本次未替用户运行新的写作模型实验，也未要求重写已交付内容来完成此分析。
