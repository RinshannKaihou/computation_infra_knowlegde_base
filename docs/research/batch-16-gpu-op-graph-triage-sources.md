## 来源案例（主案例：Inductor 把 cuSOLVER 算子放进 CUDA graph 捕获分区）

**选取**：PyTorch Issue #188355 + 修复 PR #188641（合并 commit `0ab462c59c2a26ae36624635db822125e4cb710c`）。算子/编译/图捕获交叉域，观察—归因—修复三层证据齐全，且报告自带 eager/compile 对照。

### 观察层（报错与现象）

- [Issue #188355](https://github.com/pytorch/pytorch/issues/188355)（2026-06-28 开，2026-07-11 以 COMPLETED 关闭，无评论）：环境 torch `2.14.0.dev20260624+cu130`、CUDA 13.0。含 `torch.linalg.eigh` 的函数在 `torch.compile(mode="max-autotune")` 下**第二次迭代**失败：`torch.AcceleratorError: CUDA error: operation not permitted when stream is capturing`（cudaErrorStreamCaptureUnsupported），随后 `operation failed due to a previous error during capture`（cudaErrorStreamCaptureInvalidated）；栈顶在 `torch/_inductor/cudagraph_trees.py` 的 `_record`。
- 报告自带三组对照：**eager 正常**、**max-autotune-no-cudagraphs 正常**、**max-autotune 失败**——满足「显式 eager/compile 对照」的证据形态；复现脚本 30 行内自包含。

### 归因层（上游确认的 root cause）

- [PR #188641](https://github.com/pytorch/pytorch/pull/188641)（jansel 提交、bobrenjc93 批准）正文：`torch.linalg.eigh` 经 Inductor lowering 为 fallback 算子 `aten._linalg_eigh.default`，CUDA 上由 cuSOLVER 支撑，在图捕获期间执行不安全；Inductor 的 cudagraph 分区未把该算子归类为 unsafe，故 max-autotune 可能把它放进捕获分区并在录制时失败。修复选择既有 cudagraph-unsafe 归类机制而非特判 max-autotune，理由原文照录：「the unsupported behavior belongs to the operator's CUDA implementation regardless of the compile mode that tries to capture it」。
- 注意：PR 自述「Generated by my agent」，归因文本由维护者账号署名提交并经批准合并；issue 本身无维护者评论。归因强度来自「合并的代码变更+测试」，不是来自 issue 讨论串。

### 修复层（合并与回归测试）

- 合并 commit [`0ab462c`](https://github.com/pytorch/pytorch/commit/0ab462c59c2a26ae36624635db822125e4cb710c)（2026-07-11 上 main）：`torch/_inductor/utils.py` +2 行（向 cudagraph-unsafe 算子表加 `aten._linalg_eigh.default`，注释「cuSOLVER-backed linalg.eigh is not CUDA graph capturable」）；`test/inductor/test_cudagraph_trees.py` +34 行回归测试 `CudaGraphTreeTests.test_graph_partition_max_autotune_skips_linalg_eigh`（断言 unsafe 归类、跑 issue 报告的 matmul→eigh 模式 3 次迭代、FileCheck 断言日志「Created 2 graph partitions: 1 cudagraphable, 1 non-cudagraphable」）。
- 版本归属：GitHub compare 逐 tag 验证——v2.10.0/v2.11.0/v2.12.0/v2.13.0 均不含该 commit，**v2.14.0（2026-09-02 发布）与 v2.14.1 含该修复**。
- 关键边界：回归测试带 `@skipIfRocm`，即上游回归只覆盖 CUDA；unsafe 归类表本身在框架层、后端无关，但 HIP 侧 cuSOLVER 对应物（hipsolver）的捕获安全性没有上游测试背书——**不能把该修复写成「ROCm 同样验证通过」**。
- PR 的 Test Plan 含修复前后各跑一次 issue 复现的对照与 B200 计时（eager 0.3085 ms / no-cudagraphs 0.3155 ms / 修复后 max-autotune 0.3554 ms），属提交者自述结果，本库未复现。

### 对照案例（仅观察层成立，说明「关闭≠修复」）

- [Issue #193735](https://github.com/pytorch/pytorch/issues/193735)（2026-08-16 开，2026-08-25 关闭）：ROCm 7.2.4 + torch 2.10.0+rocm7.2.4（AMD 构建）、MI350X VF（gfx950）上 `mode="max-autotune"` 多 shape 负载崩 `hipErrorStreamCaptureInvalidated`；报告内对照：单 shape 正常、default/reduce-overhead 正常、max-autotune-no-cudagraphs 正常。AMD 维护者 naromero77amd 在更新版 nightly 上未能复现，以「unable to reproduce」关闭——**无归因、无修复链**。用途：ROCm 侧症状词汇与对照写法示例，以及「issue 关闭不判成功」的实例；不可引用为已解决缺陷。
- [ROCm/rccl Issue #2022](https://github.com/ROCm/rccl/issues/2022)（2025-10-31 开，2026-01-22 因迁移至 [ROCm/rocm-systems#2785](https://github.com/ROCm/rocm-systems/issues/2785) 关闭）：捕获集合通信报 `hipErrorStreamCaptureUnsupported`；AMD 工程师定位为 RCCL 惰性初始化在捕获期调用 `hipFree()`，并称与 CUDA 行为一致（报告者在 B200 上复验 NCCL 同样不可捕获）。通信域案例，无代码修复链接；仅作 HIP 捕获错误语义与 CUDA 对齐讨论的旁证，不进主案例。

## 缺口与冲突

- **compute-sanitizer 无版本化 HTML**：`2026.3`/`2026.2`/`2025.4` 版本路径与 CUDA archive 下路径均 404；只能以「无版本 URL + Release Notes 最新条目 2026.3 + 观察日期 2026-10-09」锚定。正文引用其选项表时须标注此固定方式。
- **dl-cuda-graph 指南无版本化 URL**：versions.json 仅 latest；页面 JS 声明版本 0.16.1，2026-10-09 观察。属滚动文档，引用须带观察日期。
- **CUDA 编程指南「Prohibited and Unhandled Operations」整表本轮未抓取**：捕获禁止操作目前由 Runtime API 12.8 归档页（模式与不安全调用类别）+ PyTorch 2.6 cuda.html 约束清单 + NVIDIA 最佳实践错误码页三处覆盖；如正文需要逐 API 的权威清单，需补抓固定版本的 programming guide 对应节。
- **PyTorch 官方文档无 HIP 调试专页**：docs/2.6/notes/hip.html 为 404；AMD 侧调试口径全部来自 ROCm/HIP 文档与 ROCm pytorch-compatibility 页，正文不得写成「PyTorch 官方 HIP 调试说明」。
- **ROCm 文档结构迁移**：pytorch-compatibility 页在 docs-7.14.0 路径 404（本批用 docs-7.1.1，2025-12-10 版）；PyTorch 安装文档迁至 projects/ai-ecosystem 且未见 docs-7.14.0 版本化路径。en/latest 已为 ROCm 10.1.0（2026-10-05 发布说明），其环境变量表与 7.14.0 有个别条目语义差异（HSA_HOTSWAP_ENABLE vs DISABLE），跨版本引用必须带版本前缀。
- **rocprof 新旧工具边界**：rocprofiler（非 SDK）项目页在 docs-7.14.0 下 404；HIP 错误码页仍提「rocprof, roctracer」。正文应写 ROCprofiler-SDK 为当前口径，旧命令行工具版本归属未核对，标缺口。
- **HIP 错误码数值对齐 CUDA ≠ 行为对齐**：900–908 数值一致（HIP 官方页列出的场景描述为 HIP 侧表述）；RCCL #2022 中 AMD 工程师称 ROCm 7.0 起捕获期行为对齐 CUDA 并以 B200 复验，属工程师在 issue 内的陈述，不是版本化文档承诺。

- **主案例归因文本来源**：PR 标注「Generated by my agent」，issue 无维护者讨论；归因可信度锚定在合并代码+测试+批准人，不锚定在讨论串共识。
