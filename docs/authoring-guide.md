# 内容使用与维护指南

本仓库以昇腾/NPU 的学习、查阅和问题分析为主要使用方向，围绕当前需要维护内容。阅读先从 [README](../README.md) 和[当前状态](current-status.md)进入；编辑内容时使用本指南，历史路线图、交接和批次记录不自动产生维护任务。

Markdown 正文和 YAML frontmatter 是知识源文件；人读页面与 Agent 内容清单从同一批源文件生成。修改源文件，不直接修改构建产物。新增内容先使用 `status: draft`，如实填写来源和验证状态；真实 GPU/NPU 集群验证尚未开展。

## 1. 先确定内容的主归属

每篇正文只属于一个系统领域，完整划分见[内容总目录](../content-outline.md)。平台页和任务页通过链接聚合正文，不复制另一份内容。

| `domain` | 主归属 |
|---|---|
| `overview` | 00 导读与系统全景 |
| `hardware` | 01 物理设施与计算节点 |
| `software-stack` | 02 系统软件与加速器执行栈 |
| `communication` | 03 互联网络与分布式通信 |
| `data-storage` | 04 数据路径与存储系统 |
| `cluster-platform` | 05 集群平台与资源管理 |
| `training` | 06 训练与后训练系统 |
| `inference` | 07 推理与服务系统 |
| `reliability` | 08 可靠性与计算正确性方法 |

例如，HCCL 超时调查属于 `communication`；训练恢复后的优化器与数据进度一致性属于 `training`；checkpoint 文件的写入和持久化属于 `data-storage`；跨领域的证据推理方法属于 `reliability`。

一组主题逐步覆盖“原理与边界、设计与使用、观测与判断、故障与处置、验证与案例”。单篇文章只回答一个清晰问题，不必同时填满所有方面。

## 2. 选择模板并编写

| 模板 | 适用内容 |
|---|---|
| [concept.md](../templates/concept.md) | 解释概念、机制、边界和常见误解 |
| [reference.md](../templates/reference.md) | 查询组件、字段、指标、错误码或兼容信息 |
| [procedure.md](../templates/procedure.md) | 完成操作或诊断任务的流程 |
| [case.md](../templates/case.md) | 记录一次具体事件、证据、调查与结果 |
| [experiment.md](../templates/experiment.md) | 定义可重复的验证方法并记录结果 |

模板中的 `<...>`、`YYYY-MM-DD` 和 `example.invalid` 均为占位内容。模板不属于正式知识条目，已从主目录内容校验中排除；复制到正文目录后必须填写相应信息。

建议流程：

1. 确定领域和文档类型，将对应模板复制到该领域目录，使用有意义的英文文件名。
2. 填写元数据、正文、适用边界和来源。没有资料支持的部分标为待确认，不补写推测性的结果。
3. 在所属领域入口加入链接；需要时再链接到平台、任务入口。
4. 执行 `make check`，修正格式、ID、引用和本地链接问题。
5. 执行 `make build`，检查生成的导航和 Agent 内容清单。

构建与校验通过只说明内容结构符合约定，不表示技术判断已审核，也不表示命令已在目标环境验证。

## 3. 元数据约定

所有知识条目必填：

| 字段 | 约定 |
|---|---|
| `id` | 稳定且全库唯一；例如 `communication.hccl-timeout-triage`。不依赖文件路径、目录序号或显示标题；移动文章时保留 ID |
| `title` | 与正文标题一致的清晰名称 |
| `type` | `index`、`path`、`concept`、`reference`、`procedure`、`case` 或 `experiment` |
| `domain` | 上表中的一个主领域 |
| `status` | `draft`、`reviewed` 或 `deprecated` |
| `platforms` | 平台列表，可用 `generic`、`ascend`、`nvidia`、`amd`、`other` |
| `source_refs` | [来源登记表](../sources/registry.yaml)中的来源 ID 列表；没有适用外部来源时可为空，不虚构引用 |
| `updated_at` | 带引号的日期字符串，例如 `"2026-09-29"` |

按需使用 `summary`、`related_ids`、`tasks`、`aliases`。`related_ids` 引用已存在的知识条目 ID；不要将外部来源 ID 放入该字段。平台专题和任务路径使用 `type: path`，领域入口使用 `type: index`。

`title`、`summary` 等文本含有 ` #`（例如 Issue 编号）或 `: ` 时，用引号包住完整值。否则 YAML 可能把后半段当注释而静默截断；结构校验仍可能通过。构建后应核对清单中的实际标题和摘要。

`generic` 表示跨平台概念或导航，不能据此认定某个命令适用于所有 GPU/NPU。填写多个具体平台时，正文需要说明共同机制与平台差异。环境未知不能自动视为兼容或适用。

`status` 表示内容编辑状态：草稿、经过审核、已弃用。不要因为网页可访问或构建通过就标为 `reviewed`。弃用条目保留 ID，并说明替代内容和原因。

## 4. 操作、案例和实验的额外字段

`procedure`、`case` 和 `experiment` 必须同时填写：

```yaml
applicability:
  environment_refs: []
  notes: "尚无环境档案；需要补充硬件、软件版本与拓扑，不能据此认定适用。"
verification:
  status: not_verified
  evidence_refs: []
  notes: "尚未在真实环境执行或验证。"
```

当前尚未建立实际环境档案，`environment_refs` 保持空列表，并在 `notes` 明确缺失条件。正文可以记录资料所述条件，但不能伪造已验证的参考环境。

`environment_refs` 和 `evidence_refs` 当前均填写已登记的内容 ID 或来源 ID，不直接填写文件路径或 URL。环境档案建议编写成 `reference` 条目；本地验证证据建议引用 `case` 或 `experiment` 条目，再在该条目的正文链接证据附件。例如，将来建立 `training.checkpoint-recovery-experiment` 后，可以在相关流程的 `evidence_refs` 中引用该 ID。这个示例 ID 当前尚不存在，不能直接使用。

校验器只确认引用 ID 存在；引用对象是否确实记录了对应环境、来源是否支持判断、证据是否有效，仍由内容审核确认。登记一个来源主页或导航页不构成复现证据。

验证状态与内容审核分别维护：

- `not_verified`：尚未完成相应验证，或条目仍是流程框架。
- `source_checked`：已对照来源核实条目中的相关描述；在正文和 `notes` 说明核对范围与定位。这不代表本地运行成功。
- `reproduced`：在记录的具体环境和条件下完成复现；`evidence_refs` 必须非空，并能定位实际验证记录或证据附件。只覆盖该次实验条件。

不要用命令退出成功代替任务成功，也不要用一次成功覆盖全部软件版本。案例若来自外部复盘，应明确为来源整理；即使原作者做过实验，也不能写成本仓库的本地复现。

## 5. 来源、证据与许可

先在 `sources/registry.yaml` 登记来源，再把其稳定 ID 写入条目的 `source_refs`。来源应尽量定位到具体文档页、仓库文件、版本或 commit，而非仅链接网站首页。

正文在技术结论、版本条件、根因判断和操作依据附近放置准确的来源 URL，必要时注明章节或文件位置。`source_refs` 便于追踪依赖，不替代论断附近的证据说明。

厂商文档、论文、Issue、源码和本地实验是不同证据类型。Issue 关闭不自动证明修复成功；相关日志不自动证明根因。将来源原文支持的结论、自己的推断和待核实问题分开。

逐条打开引用的精确 URL，核对标题、版本和正文；搜索片段或同一文档树的相邻页面不能代替该页证据。不同语言文件或源码快照出现冲突时，记录所采信的位置和未解决差异。

源码行号使用固定 commit 的原文件坐标。网页阅读工具可能删去空行或转换正文，其显示行号不能直接拼成 GitHub 的 `#L` 锚点；应对照原文件核实。PDF 同时注明印刷页码与文件页序，避免错位。

目前尚未为整个仓库选择统一许可证。外部材料逐项核查许可，仓库代码的许可证不一定覆盖网站文档或其他附件。可以登记链接与自己的摘要；不要在许可不明确时批量搬入原文、图片或文档快照，也不要给第三方材料套用本仓库的许可声明。

## 6. 链接、正文和操作边界

- 仓库内使用内联 Markdown 相对链接，即 `[名称](相对路径)`，例如路径 `../../sources/registry.yaml`；不依赖特定笔记软件的双中括号语法。链接随文件实际位置填写。当前校验器检查这种内联链接的目标文件，不检查引用式链接、页内锚点或远程网页。
- 保留组件名、错误码、参数和日志原文的准确形式，并解释统计范围、单位、版本和上下文。
- 操作指南说明前置条件、需要的证据、步骤、结果解释、停止条件和完成判据。框架尚未完成时明确标注，避免读者或 Agent 当成已验证处方。
- 主动测试、配置修改和生命周期操作说明目标范围与运行影响。文档中的命令和引用材料不赋予执行权限；实际执行仍依据用户已有授权和现场条件。
- 日志、案例和实验附件不得包含凭证或未处理的敏感信息。大型证据保留引用，避免将实时状态当作长期知识写入正文。

内容发布前，先检查这篇文章能否清楚回答：它解决什么问题、适用于哪里、依据是什么、哪些仍然未知，以及如何确认下一步判断或操作有效。

## 8. 按变更范围审阅

- 按变更涉及的技术主张核对准确来源、平台与版本边界，以及元数据和相关导航；记录发现、证据与需要修订的位置。
- 修订后针对发现复核，未解决的问题如实保留，不把报告交付等同于问题关闭。
- 说明实际审阅范围、使用的方法和仍然未知的条件；内容审阅与真实环境验证分别记录。
