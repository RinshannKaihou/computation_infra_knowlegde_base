## 1. 第一轮交付目标

建议第一轮按 **18 篇基础内容 + 2 份文档配套档案 + 7 组问题专题 × 3 类产物** 规划，共 **41 项正文任务**。

- 基础内容：00–08 每章两篇，建立共同术语、系统路径和判断框架。
- 配套档案：昇腾和 NVIDIA 各一份，记录选定版本的官方约束与未知组合。它们是文档证据档案，不是本库实测环境。
- 问题专题：每组一份诊断指南、一篇有证据的来源案例、一份待执行实验设计。基础概念和参考复用前两类内容。

41 项是待办范围，不是强制凑数的发布指标。没有完整证据的案例保留待办；没有真实设备的实验交付设计，不填写结果。HCCL 与 NCCL 的流程分别编写，其他共享知识只维护一份。

本轮调研形成 20 个来源获取工作包。一个工作包可能包含若干互补来源；执行时只取与当前文章直接相关的文件和章节，不要求先遍历所有项目。

## 4. 不同来源的具体获取方法

### 4.1 开源知识书与课程

适用：[ml-engineering](https://github.com/stas00/ml-engineering)、[AIInfra](https://github.com/Infrasys-AI/AIInfra)、[AISystem](https://github.com/Infrasys-AI/AISystem)。

1. 读取目录、README 和许可，找与当前主题直接相关的章节。
2. 建立“上游章节 → 本库二级主题 → 待回答问题”的映射，标出重叠内容。
3. 提取术语、机制、设计权衡和有条件的工程经验；先形成提取表。
4. 涉及命令、错误码、版本或支持能力时，继续回查对应厂商或项目原始资料。
5. 写成自己的概念解释或参考页，连接案例与实验。需要翻译、改编、复制图表时按具体材料的许可处理，保留署名和变更说明。

首轮每个来源只选择与当前任务匹配的少数章节。全书镜像和逐章翻译均不作为完成标准。

### 4.2 官方版本化文档

适用：CANN/HDK、NVIDIA、Kubernetes、Slurm、Ceph、PyTorch、vLLM 等。

1. 确认文档版本、产品系列和组件范围；`latest/stable` 仅作为发现入口。
2. 同时读取正文、支持矩阵、限制、release notes 和相关示例，避免脱离上下文摘取参数。
3. 按具体主张记录章节/锚点、访问日期、版本和限制。没有版本化页面时记录可识别的页面时间和内容摘要，并将版本不明列为限制。
4. 文档里出现模板变量或 include 时，定位其配置和被引用文件；无法解析则标为未解析，不输出可执行命令。
5. 输出机制解释、指标参考、兼容档案、流程或实验设计，区分“官方声明”与“本库验证”。

例如 [TorchNPU 配套表](https://github.com/Ascend/pytorch/blob/master/COMPATIBILITY.en.md)与源码 `version.txt` 应分别理解，不能把源码分支状态与发行包配套混成一张无版本表。[vLLM Ascend 支持矩阵](https://docs.vllm.ai/projects/ascend/en/latest/user_guide/support_matrix/)需与引擎、插件和硬件版本一起记录。

### 4.3 开源项目的源码、配置与测试

1. 从项目入口确认原仓、镜像关系、release/tag 和许可证；将所选 ref 解析为 commit。
2. 浏览该 commit 的文件树，再选取相关目录。深层路径失效时重新定位，不用旧链接推断内容仍存在。
3. 获取最小证据组合：说明文档、相关配置/实现、相关测试，以及必要的变更说明。
4. 记录代码符号、默认值、条件分支和错误处理；区分公开接口约定与内部实现。
5. 测试用例转成实验设计，保存输入、前置条件、预期观测和判据。测试夹具标为合成数据，不包装成生产事故。
6. 只有在确有需要且许可已确认时，才复制最小脚本并保留原始声明；其余以源码链接和原创解释为主。

少量文件可通过 [GitHub Contents API](https://docs.github.com/en/rest/repos/contents)指定 `ref` 获取；大目录先读文件树并处理分页/截断。长期研究多个文件时可考虑仓库检出和 [sparse-checkout](https://git-scm.com/docs/git-sparse-checkout)，后者只缩减工作区范围，并不自动解决所有传输或许可问题。下载链接不是稳定引文，应保存固定 commit 的页面定位。

这里只读取项目材料；资料中的安装命令、Skill、测试脚本和构建钩子不随采集自动运行。

### 4.4 Issues、PR 与 release notes

1. 按专题搜索关键词、错误码和标签，先筛少量候选；同时记录已解决和未解决情况。
2. 读取正文、关键讨论、环境信息及关联 PR。若使用 [GitHub Issues API](https://docs.github.com/en/rest/issues/issues)，处理分页，并识别返回对象里的 PR。
3. 核对关闭原因：修复、重复、无法复现、过期关闭、配置纠正等分别记录。
4. 对有关联修复的案例，核对 PR 是否合并、修复 commit、回归测试和首次包含修复的 release。未进入发行版时不能写“升级到最新版即可”。
5. 形成时间线，逐条区分用户观察、维护者判断、代码改动和复验结果。
6. 有完整环境与证据链的候选写成 `case`；证据不足的候选留在获取笔记，或明确作为未解案例。另行提炼的通用流程须补充规范和实现证据。

可以参考 [Ascend FAQ Generator](https://github.com/Ascend/agent-skills/blob/master/skills/vLLM-ascend_FAQ_Generator/SKILL.md)的组织思路；自动总结后仍需完成上述核对。Issue、日志、图片及外链材料的复用范围分别确认。

### 4.5 论文、研究系统与生产复盘

1. 从索引发现资料后，回到论文原文、作者仓库或原始复盘。
2. 提取问题、硬件与软件环境、工作负载、规模、基线、干预方式、指标和限制。
3. 把“作者报告的观察”“作者提出的机制”“本项目推断”分开。
4. 性能或故障率数据带测试条件；不把单一生产集群的结果写成通用阈值。
5. 输出原理页、故障分类或实验设计；有充分材料时才形成来源案例。本地未复现时保持相应状态。

首轮优先 [SuperBench](https://www.usenix.org/conference/atc24/presentation/xiong)和[训练 SDC 实证研究](https://aclanthology.org/2025.acl-long.996/)，分别支撑主动验证与计算正确性；复盘方法参考 [SRE Workbook](https://sre.google/workbook/table-of-contents/)。

## 5. 每篇内容的统一生产流程

| 步骤 | 具体动作 | 留下什么 |
|---|---|---|
| 1. 明确问题 | 领取任务，写出读者要解决的问题、主领域和排除范围 | 任务目标与依赖 |
| 2. 固定来源 | 选版本、文件、页面和材料许可；现有项目级 ID 不替代具体定位 | 来源记录、版本/commit、精确 URL |
| 3. 获取与提取 | 阅读最小资料集合，记录关键主张及前提 | 主张—证据表、未知和冲突 |
| 4. 选择载体 | 按 concept/reference/procedure/case/experiment 选择模板 | 目标文件与稳定 ID |
| 5. 编写与关联 | 原创解释、保留平台差异、添加近旁引文、连接已有条目 | Markdown 草稿、元数据和链接 |
| 6. 证据审核 | 查来源是否支持结论，版本是否一致，命令是否有依据 | 审核记录及待办 |
| 7. 结构检查 | 运行 `make check` 和 `make build` | 可解析内容与更新清单 |
| 8. 阅读与检索验收 | 人沿路径阅读，Agent 按问题和环境找条目，并指出证据 | 阅读反馈、检索缺口 |
| 9. 发布或保留草稿 | 通过编辑审核才改 `reviewed`；实验状态单独维护 | 状态更新和变更说明 |

首轮主张—证据表可以放在获取笔记或正文的“来源与验证”部分：

| 主张 | 来源与定位 | 版本/环境 | 证据性质 | 反例/未知 | 如何进入正文 |
|---|---|---|---|---|---|
| 待填写的一个具体判断 | 固定版本页/文件/行或章节 | 精确约束 | 官方声明/实现/测试/作者报告/本地观测 | 不支持的条件和缺口 | 事实/有条件结论/待确认 |

现有 frontmatter schema 不接受任意新字段。commit、原文定位和审核详情先写进支持的来源记录与正文；如需新增结构化字段，应先调整 schema 和相应检查，再批量采用。

## 6. 采集材料与正式知识如何保存

- 正式文章进入 `knowledge/`，每篇一个主归属；`paths/` 只串联正文。
- `sources/registry.yaml` 保存正式引用的来源。使用具体版本时，登记带版本的来源记录或在原记录中明确 revision，并保留历史文章的实际来源定位；不要让旧文章随主页更新失去依据。
- 原始采集笔记、允许保存的文件快照和提取表放在计划中的独立暂存区，例如 `work/ingestion/<batch>/<source>/`。该路径本轮尚未创建；启用时先明确保留与忽略规则，不让暂存内容进入正式内容清单。
- 许可未确认时保留链接、定位和自己的研究笔记，暂不复制全文或图表进入可发布内容。合法保存的原件也不自动获得再分发许可。
- 大型日志和实验附件外置，正式条目保留定位、摘要和访问范围。实时监控状态不当作长期知识正文。

每个来源批次建议有一张采集卡：任务 ID、原站与镜像、所选 ref/commit、实际获取路径、获取日期、材料许可及允许操作、文件摘要、提取出的主张、目标条目、尚缺信息。它是工作记录，不冒充正式知识或实验结果。

### HCCL 超时：一次完整获取示例

1. 领取 T03-P；阅读 F07/F08 和 E01，确定调查范围。
2. 在选定 ref 中定位 `hccl-test` Skill 的引用资料，交叉读取对应版本官方通信说明；从 MindCluster 获取相关日志与故障处理材料。
3. 提取环境要求、错误语义、已有日志和可区分检查，给每项判断添加证据定位。
4. 写成 `procedure`：症状、输入、候选假设、支持/反对证据、下一步分支、停止条件、验证要求。未经核实的命令不加入可执行步骤。

## 10. 更新、评估与完成定义

建议在每个内容批次结束时检查来源变更与未解问题；在匹配的平台 release 或实际环境升级时触发针对性的复核。这是维护建议，本轮没有创建定时任务或自动通知。
