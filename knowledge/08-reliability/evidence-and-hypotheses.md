# 诊断中的证据、假设与结论

本文回答一个问题：面对分布式 GPU/NPU 系统中互相矛盾的日志、指标和告警，怎样推进调查而不把最早看到的症状写成根因？核心做法是分开记录症状、观测、假设、证据和结论，并让每个判断都带对象、时间、范围和可反驳条件。

本文不是具体错误码流程，也不授权执行探测、故障注入、重启或配置变更。平台命令、字段和时间戳语义必须另有对应版本的资料或现场证据。

## 五种记录对象不能混用

| 类型 | 定义 | 合格写法 | 不合格的跳跃 |
|---|---|---|---|
| 症状 | 用户、业务或系统边界感知到的偏离，说明“哪里不符合预期” | “作业 A 的 step 时长在区间 W 超出已定义包络” | “网络坏了” |
| 观测 | 某个观测点对特定对象、时刻/区间和字段留下的原始或派生记录 | “host H、process P 的日志在本地时间 t 记录错误 E；时钟误差未知” | “没有这条日志，所以事件没有发生” |
| 假设 | 能连接症状与观测、并产生可检验预测的候选机制 | “若 rank 7 的输入生产先变慢，则其 batch-ready 应先于其他 rank 出现偏移，而链路退化不必出现” | “大概率还是老问题” |
| 证据 | 带来源、对象、时间、处理方法和限制的观测，被用于支持、反驳或保留某项假设 | “同一 step ID 下，rank 7 的 batch-ready 晚于对照 rank；采集覆盖 8/8 rank” | “图上看起来相关” |
| 结论 | 在给定范围内，经过竞争假设比较后仍成立的判断；包含置信度、未解释项和有效边界 | “本次尝试中，H1 最能解释已对齐证据；H2 被该测试反驳；H3 未检查” | “已找到唯一根因” |

Google SRE 的监控章节把“什么坏了”称为症状，把“为什么”称为原因，并提醒多层系统中一个组件的症状可能成为上层的原因（[Monitoring Distributed Systems，“Symptoms Versus Causes”](https://sre.google/sre-book/monitoring-distributed-systems/#symptoms-versus-causes)）。因此，“所有 rank 在 collective 超时”可以是作业症状；它不能直接证明每个 rank 的网络都故障。

Google SRE 的排障章节把诊断描述为假设—演绎循环：从观测和系统模型提出候选原因，再寻找支持或反驳证据，或在可控条件下测试（[Effective Troubleshooting，“Theory”与“Test and Treat”](https://sre.google/sre-book/effective-troubleshooting/)）。本文在此基础上增加面向 AI 分布式作业的对象、时钟和覆盖记录；这部分是知识库原创整理。

## 先对齐对象，再排列时间

跨 rank 调查中，时间相近不代表属于同一次工作，编号相同也不代表是同一个对象。建议每条证据尽量保留以下关联键：

| 轴 | 建议字段 | 容易混淆的情况 |
|---|---|---|
| 运行身份 | 作业、run、attempt、重启代次、租户或服务版本 | 作业重启后复用名称；弹性伸缩改变成员 |
| 进程身份 | global/local rank、进程、容器、Pod/实例、主机 | rank 重新映射到新主机；容器 ID 变化但业务名不变 |
| 设备身份 | 物理设备、切分实例、运行时设备号、总线/板内位置 | 容器内序号不等于主机物理序号；设备被重新分配 |
| 工作身份 | step、microbatch、请求、collective 序号、checkpoint 或数据游标 | 不同流水阶段拥有相同局部编号；重放导致编号重复 |
| 观测来源 | 日志文件/流、指标、trace、控制面事件、探针、校验器 | 同名字段来自不同层，采样和聚合语义不同 |

时钟也应作为证据对象记录，而不是默认全局可比较：

- 保存时间源和时钟域：主机墙钟、主机单调时钟、设备事件时钟、trace 相对时间或控制面接收时间；
- 保存同步或换算方法、采集时的偏移估计与不确定度；没有依据时不要把毫秒级先后写成因果顺序；
- 优先用 step、请求、collective、checkpoint 等逻辑关联键连接事件，再在同一对象内比较时间；
- 区分事件发生时间、组件记录时间、采集/转发时间和查询时间；缓冲、批量上报与丢样会改变表面顺序；
- 记录覆盖：应有多少 rank、实际有多少 rank、缺失发生在哪个窗口。跨 rank 最大值或“最慢 rank”不能由部分样本冒充。

[训练数据供给路径与等待](../04-data-storage/training-data-path.md)也要求在同一 batch/step 与 rank 口径下连接队列、传输和消费边界；[设备资源状态链](../05-cluster-platform/device-resource-chain.md)说明节点名、Pod/容器、资源名和设备 ID 不对齐时，控制面与任务观察可能只是来自不同对象。

## 用支持、反驳和未知维护假设

每项假设至少写出：机制、适用对象与时间窗、若为真应看到什么、若为假或有替代原因会看到什么，以及当前状态。

| 证据状态 | 含义 | 更新规则 |
|---|---|---|
| 支持 | 观测符合该假设的特异性预测，并且来源与覆盖足以使用 | 增加可信度，不自动排除能产生同一观测的竞争假设 |
| 反驳 | 在测试前提成立时，观测与该假设的必要预测不相容 | 淘汰或缩小假设范围；先检查测试是否真的覆盖了目标路径 |
| 未知 | 没有合格观测，或对象、时间、字段语义、覆盖和质量不足 | 保持未知；列出补证条件，不把空值转成支持或反驳 |
| 混杂 | 观测同时受多个变化影响，无法把结果归给目标因素 | 拆分因素、寻找对照或把结论范围缩小 |

一个证据表可以这样记录：

```text
E07  来源=rank trace；对象=job A / attempt 2 / rank 7 / step 18422
     时间=设备相对时钟，已通过同 step 边界与主机事件对齐，误差范围待确认
     观测=batch-ready 晚于本 rank 前 100 step 的可比窗口
     对 H1=支持；对 H2=未知；限制=缺少输入 worker 分段事件
```

“支持”不是“证明”。配置变更与故障同时发生，只说明时间相关；多个对象同时告警，只说明相关故障。共同原因、传播链和故障域的区别见[可靠性维度与故障域](dimensions-and-failure-domains.md)。

### 缺日志不等于没发生

日志缺失至少有四类解释：目标事件未发生、组件没有埋点、记录或传输丢失、查询条件/身份/时间窗错误。只有在确认检测路径、采样、保留期和对象覆盖后，缺失才可能成为有强度的反驳证据。

《Silent Data Corruptions at Scale》报告的 CPU SDC 不被 CPU 错误报告机制捕获，却会跨栈传播并表现为应用问题；论文还明确把范围限定为其数据中心 CPU 研究（[arXiv:2102.11245v1，摘要与第 1 节](https://arxiv.org/pdf/2102.11245v1)）。它直接支持“无硬件错误日志不能一般性证明计算正确”这一证据原则，但不能证明某次 GPU/NPU 异常就是 SDC，也不能给 GPU/NPU 发生率。本文的合成例子因此始终把设备静默错误保留为待检假设，而不是借该论文宣布根因。

## 下一项检查要比较收益、代价和影响

排障不是把所有可用工具依次运行。下一项检查应优先缩小竞争假设，同时避免破坏证据或扩大影响。可以用下面的记录表比较候选检查：

| 项目 | 需要回答的问题 |
|---|---|
| 预期判别收益 | 哪种结果分别支持或反驳哪些假设？是否能把候选集合明显分开？ |
| 覆盖与可信度 | 是否命中正确对象、时间窗和执行路径？结果是否会受缓存、异步、采样或权限影响？ |
| 时间与资源代价 | 获得结果需要多久，占用多少 GPU/NPU、网络、存储与人员时间？ |
| 运行影响 | 会否改变负载、时序、缓存、调度或故障状态？会否增加服务风险或污染后续测试？ |
| 可逆性与证据保全 | 是否能回到原状态？是否应先保存易失日志、映射和状态快照？ |
| 执行前提 | 是否需要额外授权、维护窗口、隐私审查或平台版本说明？ |

优先考虑已有证据的重新关联、身份核对和低影响只读检查。主动改变系统的测试只有在目标、影响范围、停止条件、回滚方式和授权都明确时才进入候选。Google SRE 也提示，主动测试可能改变后续结果，例如额外资源或详细日志会改变性能与竞态；测试顺序应同时考虑可能性和风险（[Effective Troubleshooting，“Test and Treat”](https://sre.google/sre-book/effective-troubleshooting/#test-and-treat)）。

当检查结果不能区分假设时，应记录为“信息收益低”，而不是把模糊结果解释成倾向。处置可以先于根因结论，但“缓解有效”只证明影响下降；它不自动证明被改动对象是唯一根因。

## 两个原创合成短例

以下例子完全为说明记录方式而合成，不对应真实事故，不声称命令、字段、时延或行为适用于任何厂商平台。

### GPU 分布式训练慢 step

**症状：** 一个 8-rank GPU 训练作业在 `step 18422` 的耗时达到可比窗口的 4 倍，7 个 rank 显示在同一 collective 等待。

**已对齐观测：** 8/8 rank 的 run、attempt、step 和 collective 序号一致。rank 7 在同一进程的单调时钟下，从请求下一批数据到主机侧 batch 返回的耗时，相对该 rank 的可比历史窗口延长；两个埋点边界已确认，不包含后续主机到设备传输。各主机墙钟偏移尚未量化，跨 rank 的绝对先后未知。链路指标只有 6/8 rank 的覆盖。

**候选假设：** H1 为 rank 7 的主机侧取批阶段变慢；H2 为涉及 rank 7 的网络路径退化；H3 为 rank 7 的设备计算变慢。同 rank 阶段耗时支持 H1 描述的现象，但尚不能解释该阶段为何变慢，也不能证明它是整个慢 step 的起因。H2/H3 仍未知：链路覆盖不完整，设备执行和传输阶段尚未关联。

**下一项检查：** 先关联 rank 7 的输入队列等待、主机取批、传输与设备计算依赖，分别测量同一时钟域内的阶段耗时；需要跨设备时钟关联时另查校准精度。该检查预期区分主要耗时阶段及候选依赖，不能仅凭局部耗时完成跨 rank 根因排序。它复用已有 trace，影响较低；未实际执行，因此没有根因结论。

### NPU 推理恢复后的结果差异

**症状：** 一个合成 NPU 推理服务在控制面显示恢复完成后，两条固定校验样本的输出不满足事先定义的结果关系。

**观测：** 实例状态和请求成功码正常；checkpoint/模型制品的内容身份、设备映射和恢复前数据游标未完整记录；设备错误日志中未查到对应条目，但采集覆盖未知。

**候选假设：** H1 为恢复加载了不同模型制品或分片；H2 为前后处理/数据版本不同；H3 为设备侧静默计算错误。成功码只支持可访问性，校验样本反驳“恢复后结果已正确”。日志缺失不能反驳 H3，同时也没有支持 H3 的特异证据。

**下一项检查：** 先核对恢复前后的模型清单、内容摘要、配置和输入身份，再在固定条件下比较中间边界输出。该检查对 H1/H2 判别收益较高，也比改变线上设备状态的主动测试影响小。未实际执行，三项假设均不得写成事故根因。

## 结论的最低完整度

可交接或复盘的结论至少包含：

- 结论适用的作业/服务、attempt、rank/节点/设备、版本和时间范围；
- 被解释的症状和仍未解释的异常；
- 关键支持证据、反驳证据、未知项和混杂因素；
- 被排除或缩小的竞争假设，以及排除成立的前提；
- 缓解动作与根因判断是否分开，恢复正确性和性能是否另行验证；
- 置信度与能推翻当前结论的新证据；
- 若继续调查，下一项检查的收益、代价、影响和授权条件。

如果缺少可比较时钟、稳定对象身份、检测覆盖或结果 oracle，最准确的结论可能是“范围已缩小，但根因未知”。保留未知比把最接近告警的组件命名为根因更有价值。

## 来源核对范围

- [Google SRE Book：Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/)：核对假设—演绎循环、支持/反驳思路、混杂因素、主动测试副作用和保存调查记录；没有采用页面示例命令作为本文处方。
- [Google SRE Book：Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)：核对症状与原因、黑盒与白盒观测边界；没有把监控数据自动视为因果证明。
- [Silent Data Corruptions at Scale v1](https://arxiv.org/abs/2102.11245v1)：只核对论文对 CPU SDC、硬件错误报告缺口与跨栈表现的陈述；没有把 CPU 观测外推成 GPU/NPU 发生率、平台兼容性或本地事故证据。

本文没有运行任何上游程序、诊断命令或 GPU/NPU 检查，也没有生成本地日志或实验结果。对象对齐表、证据状态表和两个短例均为方法示意，仍需在具体环境中用版本化资料和授权范围验证。
