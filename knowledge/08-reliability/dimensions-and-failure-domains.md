# 可靠性维度与故障域

本文回答一个问题：怎样把“系统可靠”改写成可以测量、可以限定范围、也可以验证恢复结果的目标？答案不能只是一项在线率。一次作业可以持续运行但输出错误，可以给出正确结果但性能长尾失控，也可以重启成功却恢复到错误状态。

`generic` 表示本文的记录方法可用于不同平台，不表示 GPU 与 NPU 的指标、错误语义、恢复机制或基线相同。目标环境、工作负载和版本未知时，数值阈值与故障率都应保持 `unknown`。

## 四个维度分别回答什么

| 维度 | 要回答的问题 | “好事件”或通过条件 | 常见的错误替代 |
|---|---|---|---|
| 可用性 | 在约定范围和时段内，系统是否接受并完成了应服务的工作？ | 合格请求、训练步骤、调度尝试或服务分钟中，按约定完成的部分 | 进程存在、端口可连或请求返回状态码 |
| 正确性 | 结果、状态转换和持久化数据是否满足语义、数值与一致性约束？ | 经指定 oracle、容差、校验关系或业务不变量检查后通过的结果 | “没有报错”、loss 有值或 HTTP 200 |
| 性能稳定性 | 在可比条件下，吞吐、延迟和长尾是否维持在约定包络内？ | 工作负载、规模、拓扑和阶段可比的窗口中，指定分位数、离散度或退化幅度达标 | 一次峰值、全程平均值或设备利用率高 |
| 可恢复性 | 故障或中断后，系统能否在允许时间和损失内回到明确的可服务状态？ | 恢复时间、数据/训练进度损失、状态一致性、容量和后续稳定窗口同时达标 | 恢复命令退出为 0、进程重新出现或控制面显示 Running |

Google SRE Workbook 建议把 SLI 写成“好事件数 / 总事件数”，同时指出可用性、延迟之外，正确性、质量、覆盖率等也可以形成独立 SLO；同一规格还可能有覆盖范围和代价不同的实现方式（[Implementing SLOs，“What to Measure: Using SLIs”](https://sre.google/workbook/implementing-slos/#what-to-measure-using-slis)）。因此，四个维度可以使用统一的事件比率表达，但不能合并为一个含义模糊的“成功率”。

正确性尤其不能被协议成功代替。Google SRE 的监控章节把“HTTP 200 但内容错误”列为隐式错误，并指出错误内容往往需要端到端测试才能发现（[Monitoring Distributed Systems，“The Four Golden Signals”](https://sre.google/sre-book/monitoring-distributed-systems/#the-four-golden-signals)）。对训练或推理，同样需要定义输出、状态或数据的判定条件；本文不预设所有数值差异都应逐位一致。

性能稳定性也不是“还能跑”。SuperBench 在 Azure GPU 基础设施研究中报告，冗余可能掩盖逐步性能退化，部分链路或组件问题只在特定 AI 工作负载或并发计算通信模式下暴露；论文据此使用组件微基准和代表性端到端负载进行主动验证（[SuperBench，USENIX ATC 2024，第 1–2 节](https://www.usenix.org/system/files/atc24-xiong.pdf)）。这支持把灰色退化与完全不可用分开，但论文中的 Azure 观测、阈值和收益不能外推为其他 GPU/NPU 集群的基线或故障率。

## 一项指标至少写清八个部分

只有名称和数值的指标无法比较。每项可靠性指标至少记录：

1. **对象**：请求、样本、训练 step、rank、作业、节点、恢复尝试，或服务分钟；
2. **范围**：租户、模型、数据集、版本、地域、集群、节点组和设备类型；
3. **起点与终点**：例如从客户端发起到结果可用，从故障确认到恢复门槛持续满足；
4. **分母**：哪些事件有资格进入统计，重试、取消、预热、维护和无流量窗口如何处理；
5. **分子或失败条件**：什么算好，什么算错，超时、降级和部分结果如何归类；
6. **窗口与聚合**：滑动或固定窗口、分位数、按 rank/作业/租户加权方式，以及是否报告长尾；
7. **观测点**：客户端、服务端、控制面、设备侧或离线校验器；代理观测会漏掉什么；
8. **缺失与置信度**：未采集、采样、时钟误差、覆盖率和未知条件如何影响结论。

可用性比率的一个抽象写法是：

```text
availability = 满足可用性判据的合格事件数 / 纳入统计的合格事件总数
```

“合格”必须先定义。例如，一个被客户端在发送前取消的请求是否进入分母，与一个服务端收到后超时的请求不同。分母为零时结果应写为“无可计算样本”，不能写成 100%。Google SRE 也区分 SLI 规格与具体测量实现：服务端日志可能漏掉未到达后端的请求，而浏览器探针又可能漏掉只影响部分用户的问题（[Implementing SLOs](https://sre.google/workbook/implementing-slos/#what-to-measure-using-slis)）。

四个维度可以各自形成可审查的记录：

| 维度 | 指标例子 | 必须同时保存的限定条件 |
|---|---|---|
| 可用性 | 按时完成的合格推理请求 / 合格请求 | 客户端或服务端观测点、超时线、降级响应、重试归属、流量范围 |
| 正确性 | 通过结果检查的已检查样本 / 已检查样本 | oracle、容差、随机性控制、样本选择和检查覆盖率；未检查样本不进入“正确”分子 |
| 性能稳定性 | 在性能包络内的可比窗口 / 可比窗口 | 负载分布、batch/shape、并行规模、软硬件版本、预热阶段和拓扑 |
| 可恢复性 | 在恢复门槛内通过的恢复尝试 / 合格恢复尝试 | 故障模型、开始时刻、最大恢复时间、允许进度损失、状态校验与稳定观察期 |

这些指标彼此补充。例如，降级结果可能计入可用性，却在正确性或质量指标中失败；重试可能提高最终可用性，却扩大延迟并消耗容量；恢复后的短时吞吐达标，也不能抵消训练状态或业务数据错误。

## 故障域是共享依赖和影响边界

故障域不是“硬件故障”“软件故障”这样的原因标签。它是**一组对象因共享依赖、同一变更或同一传播路径，可能被一次故障共同影响的范围**。故障域可以嵌套，也可以跨层重叠；同一节点既属于供电域，也属于镜像版本域、调度控制面域和某个业务作业域。

| 故障域视角 | 需要画出的边界 | 常见共享依赖或传播关系 | 不能仅凭同时异常推出 |
|---|---|---|---|
| 硬件域 | 设备、主机、机箱、机架、供电、散热、PCIe 根、交换器、NIC 与上联 | 同一电源组、散热区、根端口、交换芯片、ToR 或存储路径 | 一定是硬件根因，或同型号设备具有相同物理连接 |
| 软件域 | 固件、驱动、运行时、框架后端、通信库、镜像、配置与发布批次 | 同一版本缺陷、配置模板、依赖包或发布波次可跨物理域相关失败 | 回滚或重启成功就证明根因是软件 |
| 控制面域 | 资源发现、账本、调度、分配、生命周期控制、服务发现与配置下发 | 同一控制器、状态存储、队列、租约或错误资源视图影响多个工作负载 | 数据面不可用，或控制面显示健康就代表任务正确运行 |
| 业务域 | 租户、作业、模型、数据分片、请求类型、版本流量与下游依赖 | 同一输入分布、模型缺陷、数据污染、热点分片或同步作业放大局部慢点 | 基础设施必然有故障，或未受影响业务可作为完全等价对照 |

硬件物理关系的记录字段见[计算节点资源与拓扑参考](../01-hardware/resource-topology.md)；物理设备、资源账本、分配与框架可用之间的控制面边界见[从物理设备到容器资源的状态链](../05-cluster-platform/device-resource-chain.md)。这些文章能帮助建立候选故障域，不能替代现场时点的共享依赖证据。

### 共同原因与相关故障要分开

- **共同原因故障**：存在一个有证据支持的共享触发因素，例如同一上联、配置发布或状态存储故障，足以解释多个对象异常。
- **相关故障**：多个异常在时间、对象或统计上相关，但共同原因尚未确认。它也可能来自传播、同步屏障、共同负载、采样偏差或告警系统的同一缺口。
- **独立故障**：只有在故障域、时间窗口、检测覆盖和条件独立性有依据时才可作为建模假设；“位于不同节点”本身不够。

因此，冗余只有跨越相关故障域时才真正缩小共同失效风险。两台机器使用同一镜像和同一控制面，或两条链路共享同一上游，都可能在物理对象分离的情况下相关失败。反过来，多 rank 同时超时也可能只是一个慢 rank 经同步传播后的结果，不能把所有 rank 都写成独立故障。

## 恢复需要一组退出门槛

恢复开始和结束都应明确定义。开始时刻可以是首个用户影响、告警触发、故障确认或恢复动作开始，但不同口径不能混算。结束时刻应是预先约定的门槛持续满足，而不是某个动作返回成功。

建议至少包含以下退出条件：

- 服务重新接受目标范围内的工作，并持续通过可用性窗口；
- 输出、模型状态、优化器/数据进度或业务数据通过正确性与一致性检查；
- 延迟、吞吐和长尾恢复到当前工作负载的性能包络；
- 丢失、回放、重复执行或回滚的工作量在允许范围内；
- 恢复后容量、冗余和故障域隔离达到约定水平，已知降级被显式记录；
- 未覆盖的对象、时间段和验证条件仍标为未知。

Google SRE 的数据完整性章节主张交付“恢复系统”而不只是“备份系统”，并要求团队按不同故障模式定义数据可用性目标、实际演练和展示满足这些目标的能力（[Data Integrity，“Delivering a Recovery System”](https://sre.google/sre-book/data-integrity/#delivering-a-recovery-system-rather-than-a-backup-system)）。对 AI 算力系统，同一原则意味着 checkpoint 被读取、容器重建或作业状态变为运行中，都只是恢复链的一部分。成功返回不代表状态正确、进度连续或后续性能稳定。

## 适用边界与待确认

本文没有定义任何平台通用阈值，也没有给出故障域探测命令。指标表和四类故障域是知识库的原创结构，不是 Google SRE 或 SuperBench 发布的标准分类。SuperBench 只支持其论文所述 Azure GPU 场景中的灰色性能退化与主动验证结论，不支持 NPU 兼容性、任意集群故障率或本文四维框架的有效性证明。

把本框架用于具体环境前，仍需确认：用户与业务目标、事件和分母定义、GPU/NPU 软硬件版本、工作负载和拓扑、观测点与时钟、正确性 oracle、性能基线、恢复故障模型，以及硬件、软件、控制面和业务域的实际共享依赖。如何把这些条件组织成证据、假设和结论，见[诊断中的证据、假设与结论](evidence-and-hypotheses.md)。

- [Google SRE Book：Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)：核对症状/原因、显式/隐式错误和端到端错误内容检测；不把四个 golden signals 等同于本文四个可靠性维度。
- [Google SRE Book：Data Integrity](https://sre.google/sre-book/data-integrity/)：核对恢复系统、故障模式与恢复演练原则；不声称文中的存储故障分类完整覆盖训练状态或模型语义。
- [SuperBench，USENIX ATC 2024](https://www.usenix.org/conference/atc24/presentation/xiong)：核对灰色退化、冗余掩盖、组件与端到端主动验证的论文结论；没有运行 SuperBench，也没有复用其 Azure 数值作为目标环境基线。
